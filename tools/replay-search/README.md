# Поиск по реплеям Mechabellum

Ищет в папке реплеев игры матчи, где у заданного игрока в армии набралось
N штук заданного юнита, была куплена заданная технология и/или применён
заданный спелл — свой или вражеский. Игру запускать не нужно, зависимостей
нет — только Python (stdlib), никакого venv.

Не путать с [`../mechabellum-extract`](../mechabellum-extract): тот достаёт
таблицы баланса из клиента, этот читает записи конкретных партий. Общего кода
у них нет, ростер юнитов берётся напрямую из `Melper.Core/Data/units.json`.
Имена технологий взять оттуда нельзя — их там нет, поэтому `--tech` по имени
читает `../mechabellum-extract/data/technologies.json` (в репозитории он лежит,
пересобирается его `run.ps1`). Числовой `--tech 10912` работает и без него.
Имён спеллов нет и там, поэтому `--spell` по имени читает
`../mechabellum-extract/data/config_raw.json` (тоже в репозитории) напрямую —
заводить ради них ещё один производный файл значило бы требовать `uv` и
установленную игру ради поиска по реплеям.

## Быстрый старт

```bash
python replay_search.py --player MakTpaxep --unit Fortress --min 4 --last 15
```

```

1 match(es) in 15 replay(s)
```

```bash
python replay_search.py --player MakTpaxep --tech "Heavy Missile"
```

```
2026-08-27 10:21  Heavy Missile bought by Stormcaller round 7  2259_20260827--201533454_[MakTpaxep]VS[HYPERCRAB].grbr

1 match(es) in 104 replay(s)
```

```bash
python replay_search.py --player MakTpaxep --side opponent     --spell "Thunder Storm" --spell Rockets --spell Ion --last 40
```

```
2026-08-30 01:01  Мягколап: [Thunder Storm round 8,9; Rockets round 6; Ion round 4,8]  2259_20260830--268656622_[MakTpaxep]VS[Мягколап].grbr
2026-08-28 10:34  LeonKerrigan: [Thunder Storm round 8; Rockets round 7; Ion round 4,8,8]  2259_20260828--268646416_[LeonKerrigan]VS[MakTpaxep].grbr

2 match(es) in 40 replay(s)
```

Число — сколько юнитов стояло на поле, когда раунд игрался. Для всех раундов,
кроме последнего, оно точное; для последнего это нижняя оценка, отсюда
`at least` (почему — ниже).

| ключ | что делает |
|---|---|
| `--player` | чью сторону смотреть (обязательный) |
| `--unit` | имя из `Melper.Core/Data/units.json` или числовой id: `Fortress` = `1` |
| `--tech` | имя технологии или числовой `TechID`: `"Heavy Missile"` = `10912` |
| `--spell` | имя спелла или числовой id: `Ion` = `300006`. Можно повторять — тогда нужны все |
| `--side` | чью армию/технологии/спеллы проверять: `player` (по умолчанию) или `opponent` |
| `--min` | порог, по умолчанию 1 |
| `--last N` | только N самых свежих матчей (по дате) |
| `--round last\|any` | считать в последнем раунде (по умолчанию) или в любом |
| `-v` | распечатать полный состав армии по попаданиям |
| `--dir` | другая папка реплеев |

Хотя бы один из `--unit` / `--tech` / `--spell` обязателен. Вместе они дают
«И»: матч должен подходить по всем, в строке появляются хвосты
`[Heavy Missile: Stormcaller round 7]` и `[Ion round 4,8]`.

`--player` всегда выбирает **матчи** (те, где этот игрок есть), а `--side` —
**чью сторону** в них смотреть. `--side opponent` проверяет всех остальных
игроков матча, каждого отдельно, и печатает имя в начале строки: искать
«партию, где противник применил X» иначе нечем — имени противника заранее
не знаешь.

Опечатка в имени игрока, юнита, технологии или спелла — это ошибка с ненулевым
кодом возврата, а не пустой список: «ничего не нашлось» всегда значит именно это.

## Как ищутся технологии

Технология покупается один раз и действует до конца партии, поэтому `--tech` —
свойство **матча**, а не раунда: `--round` и `--min` на него не влияют,
`actionRecords` просматриваются во всех раундах, а в выводе печатается раунд
покупки. Ищется `PAD_UpgradeTechnology`: `UID` — юнит, `TechID` — сама
технология.

Имя технологии берётся из `iconName` (`UT_Heavy_Missile` → `Heavy Missile`) —
поле `name` в дампе китайское, и его тоже можно передать. Одно имя часто
покрывает несколько юнитов (`Attack Range Increase` — 48 строк, по одной на
юнит); тогда засчитываются все их `TechID`, а юнит печатается по каждому
попаданию, а не выдаётся «ambiguous».

`TechID` — это `<префикс><id юнита>`, и с клиента 2276 id юнитов пишутся со
сдвигом +5000, вместе с хвостом `TechID`: `Charge Station` Вихря — `180931`
в старых реплеях и `18095031` в новых. Ищутся обе формы. У 81 технологии
`TechID` на id юнита не заканчивается (`110291` у Бездны) — сдвигать там
нечего, ищется только старая форма. Числовой `--tech` ищется буквально как
передан — обе формы подставляются только при поиске по имени.

## Как ищутся спеллы

Спелл (skill командира) — это `PAD_ReleaseCommanderSkill`, и считается он, как
технология, по всему матчу: `--round` и `--min` не при чём, в выводе печатаются
все раунды применения. Два подвоха, и каждый по отдельности превращает журнал
вражеских спеллов не в ошибку, а в тишину:

- **`<ID>` заполнен только у той стороны, которая писала реплей.** У всех
  остальных там `0`, и смысл несёт только `<SkillIndex>` — номер слота в
  `playerData/commanderSkills` этой стороны. Из 1768 применений по всем файлам
  свой `ID` несут 889, остальные 879 приходится разрешать через слоты.
- **Снапшот слотов отстаёт на раунд**: купленный в раунде N спелл появляется в
  списке только в N+1. Поэтому применение в раунде N читается по слотам,
  известным к раунду N+1, и не позже.

Не позже — принципиально. Заглядывать в более поздние снапшоты заманчиво (так
разрешается ещё несколько применений), но в реплеях, где список слотов начинает
писаться только с середины партии, поздний список ничего не говорит о ранних
раундах. Проверено против тех 889 применений, у которых `ID` свой и известен:

| правило | совпало | наврало | не опознано |
|---|---:|---:|---:|
| слоты из любого снапшота матча | 845 | **4** | 40 |
| **слоты к раунду N+1** (что и сделано) | 842 | **0** | 47 |

Неопознанные не выкидываются, а считаются: в строке появляется хвост
`+N cast(s) no snapshot names yet`. Всего таких по папке 53 из 1768.

Имя спелла берётся из `iconName` (`SW_Thunder_Storm` → `Thunder Storm`) — это
внутреннее имя, и с игровым оно совпадает не всегда: орбитальная бомбардировка
это `Rockets`, ионная — `Ion`, шторм — `Thunder Storm`. Поле `name` в дампе
китайское, его тоже можно передать. Одно имя обычно покрывает несколько id
(тир или переработка получают свой): `Thunder Storm` — это и `300005`, и
`300009`, засчитываются оба. Id, которых в дампе нет (клиент новее дампа —
например `900010`), ищутся числом и печатаются как есть.

К id спеллов сдвиг +5000 из клиента 2276 отношения не имеет: по всем файлам
ни одного id с пятёркой впереди нет, снапшот слотов в новых реплеях пишется
по-прежнему.

## Формат `.grbr`

Это поток .NET `BinaryFormatter` (`GameRiver.Replay`), внутри которого вся
партия лежит **одной XML-строкой** `<BattleRecord>`. Разбирать сам
BinaryFormatter не нужно: XML вырезается по `<?xml` и последнему
`</BattleRecord>`, дальше обычный `ElementTree`.

Сразу за этой строкой идут 8 байт — `CreateTime`, .NET `DateTime`:
тики от `0001-01-01` в младших 62 битах, `DateTimeKind` в старших двух.
Сортировка идёт по нему, а не по `mtime` (тот слетает при копировании файлов)
и не по дате из имени файла — она отличается от реальной, похоже, часовым поясом.

Внутри XML: `playerRecords/PlayerRecord` (по одному на игрока, есть `name`)
→ `playerRoundRecords/PlayerRoundRecord` (по одному на раунд) → в нём
`playerData/units`, `playerData/commanderSkills` и `actionRecords`.

Записан реплей всегда с чьей-то стороны, и это видно в данных: часть полей
действия заполнена только у неё. У `PAD_ReleaseCommanderSkill` это `<ID>` —
у остальных сторон там `0` (см. выше).

Проверено на всех 345 файлах в папке, версии клиента от `1718` (авг 2025)
до `2207` — парсятся все, включая переименованные вручную.

## Как считается состав армии

`playerData/units` — это снапшот **на входе в раунд**, его пишет сама игра.
Значит состав раунда N берётся из снапшота раунда N+1: там уже учтено всё,
что игрок в раунде N докупил и что получил бесплатно. Это точная цифра,
и именно она используется для всех раундов, кроме последнего.

**У последнего раунда следующего снапшота нет**, поэтому он считается как
снапшот + покупки по ходу раунда (`actionRecords` → `PAD_BuyUnit`, поле `UID`
— *не* `unitID`). Это **нижняя оценка**, потому что:

- Юниты из карточек подкрепления (`PAD_ChooseReinforceItem`) и стартовый отряд
  (`PAD_ChooseAdvanceTeam`) выдаются **бесплатно** — никакого `PAD_BuyUnit`
  для них нет, и что именно выдала карточка, в реплее не записано.
- `PAD_Undo` не содержит цели — он просто отменяет предыдущее действие.
  Поэтому действия раунда прогоняются через LIFO-стек, и отменённые покупки
  выкидываются.

Насколько врёт эта оценка — измерено по данным: для 5296 переходов раунда
снапшот следующего раунда показывает, что прибавилось на самом деле.

| модель | завышает | занижает |
|---|---:|---:|
| считать все `PAD_BuyUnit` подряд | 631 | 1887 |
| **со стеком отмен** (что и сделано) | **55** | 1913 |

Занижение — это ровно бесплатные юниты из подкреплений; отсюда «не меньше чем».
Завышение (1%) — остаток, в котором стек отмен угадал не то действие.

### Может ли армия уменьшаться

Действия **игрока**, продающего юнита, в данных нет — среди всех `PAD_*`,
встреченных по всем файлам, такого типа не нашлось. Но `MAD_*` (действия
режиссёра матча, песочница и спецрежимы) юнитов убирать умеют:
`MAD_RemoveUnit` (156 штук по всем файлам) и `MAD_ClearUnit` (26). Снапшоты
действительно иногда уменьшаются между соседними раундами. На точную ветку
(все раунды кроме последнего) это никак не влияет — там цифра берётся из
снапшота как есть; врать может только оценка последнего раунда.

### Раунды, которые не игрались

У 27 сторон из 690 последняя запись раунда пустая — ни одного действия.
Это почти всё игры против бота и песочница. Такие строки помечаются
`round has no actions`, чтобы «состав в последнем раунде» не путать
с составом раунда, который никто не отыграл.

## Куда НЕ ходить

- **`ProjectDatas/GameData.grdb`** — открытый XML, но там локальный сейв игрока
  (настройки, скины, блок-лист), истории матчей нет.
- **Дата в имени файла** (`2207_20260725--...`) — не совпадает с реальным
  временем партии, сортировать по ней нельзя.
- **`d.rfind(b'>')`** для поиска конца XML — работает, но случайно: после
  документа идут байты `CreateTime` и трейлер, и любой `0x3E` среди них уводит
  границу. Резать надо по `</BattleRecord>`.
