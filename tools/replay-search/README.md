# Поиск по реплеям Mechabellum

Ищет в папке реплеев игры матчи, где у заданного игрока в армии набралось
N штук заданного юнита. Игру запускать не нужно, зависимостей нет — только
Python (stdlib), никакого venv.

Не путать с [`../mechabellum-extract`](../mechabellum-extract): тот достаёт
таблицы баланса из клиента, этот читает записи конкретных партий. Общего кода
у них нет, ростер имён берётся напрямую из `Melper.Core/Data/UnitsCollection.cs`.

---

## Быстрый старт

```bash
python replay_search.py --player MakTpaxep --unit Fortress --min 4 --last 15
```

```
2026-07-23 21:53  round  9  Fortress 10 (at least; final round)  2207_20260724--134312726_[halo]VS[MakTpaxep].grbr

1 match(es) in 15 replay(s)
```

Число — сколько юнитов стояло на поле, когда раунд игрался. Для всех раундов,
кроме последнего, оно точное; для последнего это нижняя оценка, отсюда
`at least` (почему — ниже).

| ключ | что делает |
|---|---|
| `--player` | чью сторону смотреть (обязательный) |
| `--unit` | имя из `UnitsCollection.cs` или числовой id: `Fortress` = `1` |
| `--min` | порог, по умолчанию 1 |
| `--last N` | только N самых свежих матчей (по дате) |
| `--round last\|any` | считать в последнем раунде (по умолчанию) или в любом |
| `-v` | распечатать полный состав армии по попаданиям |
| `--dir` | другая папка реплеев |

Опечатка в имени игрока или юнита — это ошибка с ненулевым кодом возврата,
а не пустой список: «ничего не нашлось» всегда значит именно это.

---

## Формат `.grbr`

Это поток .NET `BinaryFormatter` (`GameRiver.Replay`), внутри которого вся
партия лежит **одной XML-строкой** `<BattleRecord>`. Разбирать сам
BinaryFormatter не нужно: XML вырезается по `<?xml` и последнему
`</BattleRecord>`, дальше обычный `ElementTree`.

Сразу за этой строкой идут 8 байт — `CreateTime`, .NET `DateTime`:
тики от `0001-01-01` в младших 62 битах, `DateTimeKind` в старших двух.
Сортировка идёт по нему, а не по `mtime` (тот слетает при копировании файлов)
и не по дате из имени файла — она отличается от реальной, похоже, часовым поясом.

Внутри XML: `playerRecords/PlayerRecord` (по одному на игрока, есть `name`)
→ `playerRoundRecords/PlayerRoundRecord` (по одному на раунд) → в нём
`playerData/units` и `actionRecords`.

Проверено на всех 345 файлах в папке, версии клиента от `1718` (авг 2025)
до `2207` — парсятся все, включая переименованные вручную.

## Как считается состав армии

`playerData/units` — это снапшот **на входе в раунд**, его пишет сама игра.
Значит состав раунда N берётся из снапшота раунда N+1: там уже учтено всё,
что игрок в раунде N докупил и что получил бесплатно. Это точная цифра,
и именно она используется для всех раундов, кроме последнего.

**У последнего раунда следующего снапшота нет**, поэтому он считается как
снапшот + покупки по ходу раунда (`actionRecords` → `PAD_BuyUnit`, поле `UID`
— *не* `unitID`). Это **нижняя оценка**, потому что:

- Юниты из карточек подкрепления (`PAD_ChooseReinforceItem`) и стартовый отряд
  (`PAD_ChooseAdvanceTeam`) выдаются **бесплатно** — никакого `PAD_BuyUnit`
  для них нет, и что именно выдала карточка, в реплее не записано.
- `PAD_Undo` не содержит цели — он просто отменяет предыдущее действие.
  Поэтому действия раунда прогоняются через LIFO-стек, и отменённые покупки
  выкидываются.

Насколько врёт эта оценка — измерено по данным: для 5296 переходов раунда
снапшот следующего раунда показывает, что прибавилось на самом деле.

| модель | завышает | занижает |
|---|---:|---:|
| считать все `PAD_BuyUnit` подряд | 631 | 1887 |
| **со стеком отмен** (что и сделано) | **55** | 1913 |

Занижение — это ровно бесплатные юниты из подкреплений; отсюда «не меньше чем».
Завышение (1%) — остаток, в котором стек отмен угадал не то действие.

### Может ли армия уменьшаться

Действия **игрока**, продающего юнита, в данных нет — среди всех `PAD_*`,
встреченных по всем файлам, такого типа не нашлось. Но `MAD_*` (действия
режиссёра матча, песочница и спецрежимы) юнитов убирать умеют:
`MAD_RemoveUnit` (156 штук по всем файлам) и `MAD_ClearUnit` (26). Снапшоты
действительно иногда уменьшаются между соседними раундами. На точную ветку
(все раунды кроме последнего) это никак не влияет — там цифра берётся из
снапшота как есть; врать может только оценка последнего раунда.

### Раунды, которые не игрались

У 27 сторон из 690 последняя запись раунда пустая — ни одного действия.
Это почти всё игры против бота и песочница. Такие строки помечаются
`round has no actions`, чтобы «состав в последнем раунде» не путать
с составом раунда, который никто не отыграл.

## Куда НЕ ходить

- **`ProjectDatas/GameData.grdb`** — открытый XML, но там локальный сейв игрока
  (настройки, скины, блок-лист), истории матчей нет.
- **Дата в имени файла** (`2207_20260725--...`) — не совпадает с реальным
  временем партии, сортировать по ней нельзя.
- **`d.rfind(b'>')`** для поиска конца XML — работает, но случайно: после
  документа идут байты `CreateTime` и трейлер, и любой `0x3E` среди них уводит
  границу. Резать надо по `</BattleRecord>`.
