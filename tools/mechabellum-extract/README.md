# Извлечение данных из клиента Mechabellum

Автономный (headless) экспорт таблиц баланса прямо из файлов игры в JSON/CSV.
Игру запускать не нужно, сеть не нужна, GUI-инструменты не нужны.

Нужно это для того, чтобы `Melper.Core/Data/units.json` не заполнять руками,
а сверять с реальными данными игры после каждого патча.

---

## Быстрый старт

Из папки `tools/mechabellum-extract`, всё одной командой:

```bash
.\run.ps1
```

Окружение он создаст сам, если его нет (нужен только `uv` в PATH). Со сверкой против
`Melper.Core/Data/units.json`:

```bash
.\run.ps1 -Compare
```

Занимает около минуты, из них почти всё — разбор `global-metadata.dat`.
Требуется единственная внешняя вещь: **установленная игра**. Путь к ней — константа
`GAME` в начале `scripts/dump_all.py`.

<details>
<summary>Если хочется вручную, без run.ps1</summary>

```bash
uv venv --python 3.11 .venv && uv pip install --python .venv\Scripts\python.exe -r requirements.txt
```

Дальше по порядку (`make_units` читает то, что положил `dump_all`):

```bash
.venv\Scripts\python.exe scripts\dump_all.py && .venv\Scripts\python.exe scripts\make_units.py
```
</details>

## Связь с `Melper.Core/Data/units.json` — по `Id`

`Unit.Id` — это **`MechData.id` самой игры**. Имена не годятся как ключ: они меняются
с локализацией и переводом, id — нет. Поэтому никакого маппинга имён в проекте больше
нет, `compare_with_csharp.py` джойнит строго по `Id`.

Файл устроен так — дата лежит рядом с числами, которые она описывает:

```json
{
  "Date": "2026-08-01",
  "Units": [ ... ]
}
```

**Когда в игру добавят юнит**, сверка сама выведет готовый блок JSON для вставки —
с китайским именем как заглушкой, его потом переименовать вручную:

```
=== 1 roster unit(s) missing from units.json ===
  {
    "Id": 31,
    "Name": "磁暴",
    ...
  },
```

Обратное тоже ловится: если id из ростера исчез из игры, будет `NOT IN GAME DATA ANY MORE`.

### Про ПВО

`CanAttackAir` в `Unit` означает **врождённое** ПВО. Шесть юнитов получают его только
покупной технологией (`防空弹药` и родственные) — у них `CanAttackAirWithTech`:
Fortress, Arclight, Sandworm, Tarantula, Void eye, Mountain. В данных это колонки
`vsAir` и `vsAirTech`; вторая вычисляется по описаниям технологий юнита, где ищутся
формулировки вида «может атаковать воздушные цели» (а не «больше урона по воздуху»).

## Как устроена игра

Unity **2022.3.62f3**, сборка **IL2CPP** (`GameAssembly.dll` + `global-metadata.dat`),
namespace разработчика — `GameRiver`. Ассет-бандлы обычные `UnityFS`, **без шифрования**.

Все конфиги лежат в одной сцене **`Mechabellum_Data/level0`** — шесть соседних
MonoBehaviour-компонентов:

| класс | что внутри |
|---|---|
| `ConfigDataContainer` | 58 таблиц: `mechDatas` (юниты), карты, баффы, офицеры, магазин |
| `MechSkillGroupData` | 112 оружий: дальность, интервал атаки, сплэш, ПВО |
| `TechnologyGroupData` | 108 технологий (апгрейды юнитов) |
| `EquipmentGroupData` | снаряжение |
| `CommanderSkillGroupData` | скиллы командира |
| `ContraptionGroupData` | башни/устройства |

> `path_id` **намеренно не зашиты** в скрипт: он находит объекты по имени класса через
> реестр `MonoScript`. При патче игры номера меняются, а имена — нет.

## Как работает извлечение

TypeTree в релизной сборке **вырезан**, поэтому в два шага:

1. `TypeTreeGenerator` (UnityPy + TypeTreeGeneratorAPI) восстанавливает раскладку полей
   прямо из `GameAssembly.dll` + `global-metadata.dat`. **DummyDll не нужен** — метод
   `load_local_game()` жуёт IL2CPP напрямую.
2. Сырые байты MonoBehaviour разбираются **вручную** (`Reader` в `dump_all.py`), потому что
   штатный ридер UnityPy не понимает, как генератор именует узлы-контейнеры
   (`m_Type` контейнера равен типу элемента, а не `vector`).

### Три грабли, на которые я наступил

Каждая ломает разбор полностью, и симптом всегда один — «insane count», потому что
смещение уезжает и длина массива читается из мусора.

| # | Грабля | Как чинится |
|---|---|---|
| 1 | У `m_Enabled` в заголовке нет флага выравнивания `0x4000`, хотя Unity после однобайтового поля всегда выравнивает до 4 | флаг проставляется принудительно |
| 2 | `List<string>` имеет **тот же** `m_Type="string"`, что и обычная строка | строка — только если элемент массива типа `char`, иначе массив |
| 3 | `m_Name` в заголовке — узел `string` **вообще без** дочернего `Array` | обрабатывается как бездетная строка |

### Как убедиться, что распарсилось верно

Главный критерий — **прочитано ровно столько байт, сколько в объекте**, без остатка.
При неверной раскладке смещение уезжает и остаток не сойдётся. Скрипт проверяет это сам
и роняет контейнер в `FAIL`, если не сошлось.

Дополнительно: `m_Script.m_PathID` каждого объекта обязан совпадать с `path_id` его
класса-`MonoScript`, а расшифрованные `FPoint` должны давать ровные числа
(дальность 100 / 140 / 180, интервал 0.1 / 1.8) — при неверном делителе была бы каша.

## Куда НЕ ходить (проверенные тупики)

- **`ProjectDatas/GameData.grdb`** — заманчиво выглядит (это открытый XML!), но там
  локальный сейв игрока: настройки, скины, блок-лист. Баланса нет.
- **`StreamingAssets/aa/*.bundle`** (Addressables) — по `catalog.json` там только
  `Assets/Config/Skin`, `Assets/Prefabs/UI` и видео. Баланса нет.
- **`globalgamemanagers.assets`** — грепом там находится строка `ConfigDataContainer`,
  но это лишь реестр из 5993 `MonoScript` (имена классов), а не данные. Не обмануться.
- **Перехват трафика** (Wireshark / mitmproxy) — бессмысленно. В `StreamingAssets/EOS`
  лежат конфиги Epic Online Services: сеть нужна только для матчмейкинга. Баланс целиком
  в клиенте, иначе не работали бы детерминированная симуляция боя и реплеи.
- **GUI-инструменты** (AssetStudio, AssetRipper, UABEA) — рабочий вариант, но лишний:
  цель локализована до одного объекта, а headless-скрипт повторяем и не требует кликов.

## После патча игры

1. Прогнать `dump_all.py` — он сам найдёт объекты по именам классов.
2. Если появился `WARNING: not found` — класс переименовали. Найти новое имя можно
   грепом по `dump.cs` (см. ниже) и поправить `TARGET_CLASSES`.
3. Если контейнер упал в `FAIL` с несошедшимся числом байт — поменялась структура полей.
   Смотреть новые поля в `dump.cs`.
4. Прогнать `compare_with_csharp.py` и перенести изменения в `Melper.Core/Data/units.json`.
5. Там же поднять `"Date"` на текущую дату — её показывает страница Data в веб-приложении
   и через полгода начинает предупреждать, что числа пора перепроверить.

**Если понадобится смотреть исходный C#-код игры** (например, разобраться в новом поле):

```bash
winget install --id Perfare.Il2CppDumper
```

```bash
Il2CppDumper.exe "<game>\GameAssembly.dll" "<game>\Mechabellum_Data\il2cpp_data\Metadata\global-metadata.dat" <outdir>
```

Получится `dump.cs` (~38 МБ) со всеми классами и полями — грепать, не открывать целиком.
В конце утилита падает на «press any key» — это нормально, файлы уже записаны.
Основная сборка игры — `GRCore.dll` / `GRClient.dll`.

## Модель данных

**`MechData`** — сам юнит:
`life` (生命值 — HP), `damage` (基础攻击力), `moveSpeed`, `isFly`,
`attackStrength` (урон по строениям), `attackAngle`, `rotateSpeed`, `radius`,
`mainSkillID` → ссылка на `SkillData`.

`mechType` — enum `GameRiver.UnitType`: **0 = Small, 1 = Medium, 2 = Huge**.
Это размерный класс, *не* «земля/воздух» — за полёт отвечает отдельный `isFly`.

**`SkillData`** — оружие: `attackRange` (攻击范围), `attackDuration` (интервал атаки),
`splashRange` (溅射范围), `canAttackGround` / `canAttackAir`, `minAttackRange`,
`weaponCountPerSkill`, `damageRate`, `weapons`.
Подтипы лежат отдельными списками: `projectileSkillDatas`, `laserSkillDatas`,
`sweepSkillDatas` и т.д. — все наследуют `SkillData`, поэтому индексируются по `id` в кучу.

**`FPoint`** — не float, а **fixed-point Q32.32** (нужен для детерминированной симуляции):
реальное значение = `m_rawValue / 2^32`. Парсер приводит сам и округляет до 6 знаков,
иначе `0.2` выглядит как `0.19999999995343387`.

## Где в данных встречаются английские имена

Отдельного маппинга имён проект не ведёт (ключ — `Id`), но если понадобится, перевод
местами лежит прямо в данных: в таблице `surviveUnitDatas` строки названы
`"堡垒-Fortress"` и несут `unitID`. Покрывает только юнитов 1–19.

Ловушка: дефис в именах встречается и в других таблицах, но там это **не** переводы
(`犀牛-5001` — имя-ID скилла, `骇客-散射` — китайский-китайский). Брать надо именно
`surviveUnitDatas` и только строки с латиницей.

Полная локализация на любой язык — в `LanguageSourceAsset` (I2 Localization),
это отдельный нереализованный шаг.

## Как отличить юнита основной игры от служебного

Признак лежит в `cardDatas` — поле **`specialUnit`**. Оно делит все 63 юнита начисто:

| `specialUnit` | колонка `roster` | сколько | что это |
|---:|---|---:|---|
| 0 | `main` | **32** | обычный ростер: id 1–31 плюс 2002 (Mountain) |
| 1 | `special` | 2 | титаны-спецы: `丧钟` и его экспериментальная версия |
| 2 | `survive` | 27 | режим выживания: все `试验级*`, `补给船` и т.п. |
| 3 | `summon` | 2 | призываемые: `幼虫` (личинка), `蜘蛛雷` (паучья мина) |

Проверено, что разделение точное: множество `specialUnit == 0` совпало ровно с тем
ростером, который независимо подтверждается `Melper.Core/Data/units.json`. Соседние поля
(`isTestUnit`, `defaultUnlockType`) похожи, но дают по 2 исключения — брать надо
именно `specialUnit`.

Рядом полезное поле **`group`** (колонка `tier`) — категория юнита в магазине,
у служебных всегда 0:

| tier | юниты |
|---:|---|
| 1 | Marksman, Mustang, Steel Ball, Fang, Crawler, Sledgehammer, Arclight, Fire Badger, Sabertooth, Tarantula, Hound, Void Eye, Vortex |
| 2 | Rhino, Wasp, Stormcaller, Hacker, Phoenix, Wraith, Scorpion, Typhoon, Phantom Ray, Farseer |
| 3 | Fortress, Vulcan, Melting Point, Overlord, Sandworm, Raiden |
| 4 | War Factory, Abyss, Mountain |

Оттуда же берутся ещё три поля, которые прямо ложатся в `Unit`:
`baseMoney` → `Cost`, `mechCount` → `CountInPack` (сверено: Fang 100/18,
Crawler 100/24 — совпадает с текущим C#) и `unlockPrice` → `UnlockCost`.

`unlockPrice` — цена открытия юнита в магазине на матч, и она ровно повторяет `tier`:

| tier | unlockPrice |
|---:|---:|
| 1 | 0 (стартовые) |
| 2 | 50, у Hacker — 100 |
| 3 | 200 |
| 4 | 350 |

Нулевая цена — это признак стартового юнита, по нему на странице фильтра стоит
быстрый выбор «Starters».

### Играбельный ростер = id 1–31 плюс 2002 (Mountain)

Всего 32 юнита. В `Melper.Core/Data/units.json` сейчас 31 — **не хватает `id=31 磁暴 / Vortex`**
(добавлен в игру примерно в марте 2026):

| поле | значение |
|---|---|
| стоимость (`baseMoney`) | 100, `mechCount` = 1 |
| HP / урон | 7425 / 1309 (на 1 уровне) |
| дальность / интервал | 85 / 1.5 с |
| скорость / размер | 8 / Medium |
| по воздуху | нет (`vsAir = false`) |
| описание | «дешёвый и прочный юнит передней линии, уничтожает средние юниты на средней дистанции» |

Тематика электромагнитная, технологии: `电磁云` (EMP-облако), `电磁双生` (фантомный
двойник), `移动电站` (мобильная электростанция), `射程强化` (дальность).

## Масштабирование по уровням

Таблица `attributeUpgradeDatas` (9 строк) задаёт рост статов, и он **строго линейный**:

```
level 1..9  ->  lifeRating = damageRating = level
```

То есть `HP = life × level` и `Damage = damage × level`. Модель в `Unit.cs`
(`Health => _health * Level`) этому соответствует — менять ничего не нужно.
Стоимость прокачки — в `mechExpDatas` (`upgradeLv2..9`, `upgradeSupplyLv2..9`).

## Что показала сверка с `Melper.Core/Data/units.json`

На момент последней синхронизации — **0 расхождений из 32**, коллекция совпадает с игрой.
Первый прогон показывал 23 расхождения; вот что из этого стоит помнить.

- **Расхождения шли в обе стороны** (где-то в C# было больше, где-то меньше), то есть это
  был **дрейф баланса между патчами**, а не ошибка парсинга.
- **Урон у многоударных юнитов считается иначе.** У обычных юнитов `MechData.damage`
  совпадает с C# один в один (Crawler 79 = 79). Но у лазерных (Melting Point, Steel Ball)
  `damage` — это урон **за тик** (интервал 0.2 с), а не за выстрел: 168 против 7952 в C#.
  Для них нужен множитель из `weaponCountPerSkill` / `weapons` — как раз то, для чего в
  `Unit` заведены `HitsPerAttackOverride` и `ProjectilesPerShotOverride`.
- Поле `SkillData.damage` (список по уровням) у основных скиллов **пустое** — источником
  урона служит именно `MechData.damage`.

> Вывод: `compare_with_csharp.py` — не разовая проверка, а рабочий инструмент. Гонять после
> каждого патча и переносить дельту в `Melper.Core/Data/units.json`.

## Что осталось несделанным

- **Локализация имён.** Имена юнитов в `units.csv` только китайские — английские живут
  в `Melper.Core/Data/units.json` и ключуются по `Id`. Если понадобятся имена на любом языке
  прямо из игры, они в `LanguageSourceAsset` (I2 Localization).
- **Один юнит из 63** без `mainSkillID` (сджойнено 62) — не разбирался, похоже служебный.
- **Технологии не разложены** в удобную таблицу: `TechnologyGroupData` распарсен и лежит в
  `config_raw.json` (108 штук, 51 таблица подтипов), но своего `make_*.py` для него нет.
